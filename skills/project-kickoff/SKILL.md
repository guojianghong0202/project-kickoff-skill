# 项目启动流程（Project Kickoff）

把一个模糊想法变成一份**想清楚、写清楚、对齐清楚**的可执行项目启动包。

## 工作原则

- 先判断项目量级，再决定流程深度。S 小型任务不要套重流程。
- 先问清楚，再给方案。一次只问 1-3 个关键问题，优先给选项或示例。
- 访谈最多两轮。第二轮后必须输出带 `TBD（负责人 / 截止日）` 的草案，让用户在草案上改。
- 不替用户脑补缺失信息。拿不到就显式标 `TBD`，并说明缺口、风险和建议 owner。
- 用户明确说“先别问，直接按假设给草案”时，可以直接输出，但必须先列假设。
- 不讲方法论长课。用户要的是启动推进时，直接进入访谈、草案或检查清单。
- 生成文件前先确认目标目录；不要覆盖已有 `AGENTS.md`、`README.md`、`docs/`、`CLAUDE.md`。

## 不触发边界

不要把所有计划类问题都套成项目启动。以下情况默认不使用本 skill：

- 用户只是排本周任务、拆个人待办、写日程。
- 用户只是修 bug、解释代码、做普通 code review。
- 用户只是润色文案、总结会议纪要、整理资料。
- 用户已经在执行阶段，只问一个局部实现细节。

若用户明确提到立项、启动、kickoff、项目章程、PR/FAQ、RACI、里程碑、验收标准，才按本 skill 处理。

## 操作流程

按顺序走。每一步先判断该做到什么深度，不要对小项目上重型流程，也不要对大项目省关键步骤。

### 可选第 -1 步：候选项目评分

当用户给出多个候选项目、趋势条目、GitHub/Hacker News/Product Hunt/arXiv/RSS 内容，并问“哪个值得做”“哪个适合启动”“帮我排序/打分”时，先读取 `../../references/scoring.md` 做候选评分。

评分只用于筛选优先级，不替代项目启动。选出 1-3 个高分候选后，再进入第 0 步判断项目体量。

### 第 0 步：判断项目体量，选启动深度

| 量级 | 典型特征 | 最少要产出 |
|------|---------|-----------|
| **S 小型** | 1 人、≤2 周、可逆、不跨团队 | 一段话写清：目标 + 验收标准 + 负责人。其余跳过。 |
| **M 中型** | 2–6 人、1–2 个月、跨 1–2 个团队 | 一页项目章程 + RACI + 里程碑 + 一次启动会 |
| **L 大型** | 多团队、季度级以上、不可逆/高投入/对外发布 | PR/FAQ 或六页纸 + 设计文档/RFC + RACI + 阶段关卡 + 风险登记 + 正式启动会 |

判断不准时，先问："这个项目大概几个人、做多久、出了问题好不好回头？"

### 第 1 步：收集启动输入

访谈按两轮上限推进：

- **第一轮**：只问最影响方向的 1-3 个问题，通常是体量、问题/机会、成功指标。
- **第二轮**：只补最影响落地的 1-3 个问题，通常是范围 In/Out、决策人、依赖/风险。
- **第二轮后**：必须输出草案。缺失信息用 `TBD（负责人 / 截止日）`，不要继续追问拖住用户。

必问清单：

- **问题 / 机会**：要解决谁的什么痛点？不做会怎样？
- **为什么是现在（Why now）**：什么变化让这件事此刻值得做？
- **目标客户 / 受益人**：具体是谁，不是"所有人"。
- **成功指标**：怎么量化"成了"？给出可测的数字或验收标准。
- **范围（In / Out）**：明确写"这次做什么"和"这次不做什么"。
- **干系人与决策人**：谁拍板、谁出钱、谁要被知会、谁会反对。
- **依赖与约束**：依赖哪些团队/系统/外部条件？预算、deadline、合规红线。
- **主要风险与假设**：最可能让项目翻车的三件事是什么？哪些是还没验证的假设？

主动索取相关资料：现有文档、竞品/对标、真实业务数据、公司主体与合规材料、已有代码或系统、预算与时间表、干系人名单。

需要更细的问题库时读取 `../../references/questions.md`，但不要一次性把问题库甩给用户。

### 第 2 步：产出启动文档

按第 0 步的量级，选对应产物，从 `../../references/templates.md` 取模板填写：

- **M 中型** → 一页项目章程。
- **L 大型 / 对外产品** → PR/FAQ（Working Backwards）。
- **L 大型 / 需要高管拍板** → 六页纸叙事。
- **偏技术 / 架构选型** → 设计文档 / RFC。
- **AI / 模型 / 数据类项目** → 在以上基础上补 eval、分阶段放量、安全与失败模式分析。

每份文档都必须包含：目标、可衡量的成功指标、范围 In/Out、决策权、里程碑、风险。

#### 2.x 落地项目文件

需要把方案落到仓库时，优先产出 `AGENTS.md`，按需补 `README.md`、`docs/`、`CLAUDE.md`、`.claude/launch.json`。可以使用 `../../scripts/scaffold.py` 生成骨架；脚本默认不覆盖已有文件。

### 第 3 步：对齐评审（启动会）

开一次启动会把人对齐到同一页。建议当场静读启动文档 10-20 分钟，再讨论背景目标、范围、RACI、里程碑关卡、风险依赖、行动项。会后 24 小时内发纪要，必须包含决策、待办、owner、截止日。

### 第 4 步：设定阶段关卡

给项目划出 2-4 个阶段，每个阶段末设关卡。每道关卡必须写清 exit criteria，并在关卡处做 Go / Recycle / Kill 决定。AI 项目关卡通常包括 eval 达标、灰度无重大问题、安全审查通过。

## 完成标准

- [ ] 出方案前已完成结构化访谈、关键信息/资料/数据已收齐或显式标 TBD
- [ ] 启动文档（章程 / PR-FAQ / 六页纸 / 设计文档，至少一份）
- [ ] 可衡量的成功指标 / 验收标准
- [ ] 范围 In / Out 清单
- [ ] RACI 或 DACI 决策矩阵
- [ ] 里程碑 + 阶段关卡（含放行标准）
- [ ] 风险登记表（Top 风险 + 应对 + owner）
- [ ] 启动会议程 + 会后纪要
- [ ] 项目文件已落地：`AGENTS.md`，按需 `README` / `docs/` / `CLAUDE.md`
- [ ] 所有 TBD 都挂了 owner 和截止日

输出前读取或套用 `../../references/quality-gate.md` 做自检，发现缺口就直接补在“待确认问题”里。

## 参考文件

- `../../references/templates.md`：章程、PR/FAQ、六页纸、RFC、RACI、风险、会议程、AGENTS.md 模板。需要具体模板时读取对应章节。
- `../../references/scoring.md`：候选项目评分模型。用户给多个候选项目或问“哪个值得做”时读取。
- `../../references/questions.md`：两轮访谈问题库和按项目类型分流的问题。需要追问时读取。
- `../../references/quality-gate.md`：输出前自检清单和常见跑偏反模式。交付草案前读取。
- `../../references/playbooks.md`：Amazon、Google/Meta、AI 大厂、PMBOK、Stage-Gate 等方法对照。用户问“大厂怎么做”时读取。
- `../../references/superpowers.md`：启动之后的 brainstorming、writing-plans、subagent-driven-development。用户问落地执行计划时读取。
- `../../examples/m-project-kickoff.md`：一个 M 型项目的完整填好样例。用户需要示例或输出风格不明确时读取。
